# Imaging a Li-ion Battery — McStas (neutrons) & McXtrace (X-rays)

Both codes model the *same* physical object: an approximate cylindrical (18650-type) Li-ion cell "jellyroll", built as a stack of concentric material shells using the Union framework — `LiIon_Battery_Union_Neutron.instr` (McStas, materials via NCrystal) and `LiIon_Battery_Union_Xray.instr` (McXtrace, materials via xraylib). Read either file's header comment block before starting — it documents the geometric approximation (a five-shell "onion model" of the winding: can, cathode, separator, anode, mandrel), the material choices, and every place a number was estimated rather than measured, flagged `[assumed]`.

The point of doing both is the contrast, not just the imaging: for neutrons the cathode shell's attenuation is completely dominated by natural lithium's huge capture cross-section, while for X-rays that same shell is completely dominated by cobalt instead — lithium is essentially invisible to X-rays. That complementary-contrast picture is exactly the argument made in the paper both files cite: Ziesche et al., *"Neutron imaging of lithium batteries"*, Joule 6, 35–52 (2022), [doi:10.1016/j.joule.2021.12.003](https://doi.org/10.1016/j.joule.2021.12.003) — worth a skim before or during the session.

**Before you start:** each file is a complete, valid `DEFINE INSTRUMENT`/`TRACE`/`END` instrument in its own right (`battery` for the neutron file, `battery_xray` for the X-ray one) — that's normal, not a mistake: McStas/McXtrace's `%include` mechanism fully supports nesting one instrument's definition inside another's `TRACE` section, which is exactly the trick you'll use to pull the battery into a copy of `Tomography.instr` or `PSI_ICON.instr` fetched from your own `$MCSTAS/examples` (see "How the two instruments connect" below) — neither file lives in this folder ready-made, you add the `%include` yourself. Being a complete instrument also means either file can be compiled and `mcdisplay`/`mxdisplay`'d entirely on its own (no source needed) for a quick geometry check before wiring it into a beamline. One real fix worth knowing about either way: all five nested shells have slightly staggered `yheight` values rather than one shared value, because `Union_cylinder` refuses coincident end-cap planes — see the "FIX" note in either file's header (in the geometry section) for the full explanation.

**How the two instruments connect:** every geometry component inside either `%include`'able file is positioned relative to one component, `sample_pos` (a `REMOVABLE COMPONENT Arm`) — that Arm is the file's single connecting point to whatever host ("outer") instrument includes it. `REMOVABLE` is what makes this a real connection rather than just a coincidence of names: if the host instrument declares its own component instance also called `sample_pos` — any component type, positioned and rotated wherever the battery should sit — immediately before the `%include` line, that outer `sample_pos` is the one the included geometry actually attaches to, not the fragment's own `AT (0,0,0) ABSOLUTE` placement. Concretely, once you've copied `Tomography.instr` or `PSI_ICON.instr` in from `$MCSTAS/examples`: find the `Arm` (or other component) marking the sample position in that file — it may already have a different name (the stock `Tomography.instr`, for instance, refers to it as `samplearm`) — rename it to exactly `sample_pos` (or add a new `Arm` called `sample_pos` at the same location if you'd rather leave the original untouched), remove or comment out whatever sample component was there before, and add `%include "LiIon_Battery_Union_Neutron.instr"` immediately after it — e.g. `COMPONENT sample_pos = Arm() AT (0,0,1) RELATIVE Origin ROTATED (-45,omega,10) RELATIVE Origin` followed by the `%include` line. So, to drop the battery into any instrument of your own: declare a component named `sample_pos` wherever you want it, then `%include` the battery file right after.

## McStas (neutrons)

1. **Get oriented.** Open `LiIon_Battery_Union_Neutron.instr` and read the header: the onion-model geometry, why the cathode's active material is proxied by `Li2O_sg225_LithiumOxide.ncmat` (no exact LiCoO₂/NMC/LiFePO₄ entry exists in the supplied NCrystal stdlib, but this proxy at least keeps genuine Li content — and therefore genuine Li contrast — in that shell), and the hand-computed `my_absorption` values (flagged as placeholders pending a proper `ncrystal_mcstasunion`/`nctool` calculation).
2. **Drop it into a host instrument.** Copy `Tomography.instr` or `PSI_ICON.instr` from your `$MCSTAS/examples` into your own working directory, then wire the battery in yourself as described in "How the two instruments connect" above — rename (or add) a `sample_pos` Arm at the sample position and `%include "LiIon_Battery_Union_Neutron.instr"` right after it. Or skip the templates and start your own host instrument (source + this `%include` at your sample `Arm` + a detector) from scratch. A ready-to-run minimal host instrument doing exactly the latter is also available in [`hints/`](./hints/) (`ex_battery_mcstas_host_starter.instr`), if you want to see the connecting-point mechanism working end to end before tackling a full template instrument.
3. **Radiography.** Run a single-angle transmission image. Where does the beam attenuate most? Check that against the header's absorption estimates — the cathode shell should dominate, and should be the shell where natural lithium is doing almost all the work.
4. **A crude stand-in for charge/discharge.** There's no real electrochemistry here, but you can mimic a change in lithiation state by editing the NCrystal `cfg` strings — e.g. changing the `Li2O_sg225_LithiumOxide.ncmat;density=0.85x` volume-fraction scaling on the cathode shell, or its `temp=` — and see how much the radiograph actually changes. Be explicit with yourself about what this is and isn't modelling.
5. **Bragg-edge imaging (conceptual).** A Bragg edge is the sudden jump in a polycrystalline material's total scattering cross-section at the wavelength matching `λ = 2d` for its largest `d`-spacing. Seeing it requires a wavelength- (or time-of-flight-) resolved measurement, not a single-wavelength radiograph — so this is a natural next step for a pulsed/TOF-capable host instrument rather than the continuous sources used here. Worth discussing even if you don't build it: which of the battery's shells would show the clearest Bragg edges, and why might that matter for imaging state-of-charge?
6. **Full CT.** `Tomography.instr`'s own header already documents the recipe: `mcrun Tomography.instr offfile=... -n1e4 -N18 omega=0,340 -d TomoScan` (note: real statistics need far higher `ncount` than that), followed by the shipped `tomo_recon.m` (needs Matlab's imaging toolbox) to reconstruct a 3D volume — `isosurface` is a reasonable way to pull out a rendered surface once you have it.

## McXtrace (X-rays)

1. **Get oriented.** `LiIon_Battery_Union_Xray.instr` is deliberately a complete, standalone instrument (its `sample_pos` `Arm` is marked `REMOVABLE`) so you can `mxdisplay` it on its own to sanity-check the geometry before wiring it into a beamline. Read its header too — it's worth comparing side-by-side with the neutron file's: same onion-model shells, but here the cathode is built from LiCoO₂'s *real* Li/Co/O stoichiometry rather than an oxide proxy, because xraylib's per-element processes don't need a curated compound library the way NCrystal does.
2. **Build a host instrument.** Either copy `Airport_scanner.instr` from your `$MCXTRACE/examples` into your own working directory and adapt it the same way (rename/add a `sample_pos` component at the sample position, `%include "LiIon_Battery_Union_Xray.instr"` right after it — see "How the two instruments connect" above), or start fresh: a source (`Source_flat`/`Source_gaussian`), a `sample_pos` component, the `%include`, and a flat `PSD_monitor` downstream. Manually trimming the file down to just its `Union_init` … `Union_stop` components is the alternative if you'd rather reuse the Union block some other way. A ready-to-run minimal host instrument for the "start fresh" route is also available in [`hints/`](./hints/) (`ex_battery_mcxtrace_host_starter.instr`).
3. **Pick a beam energy deliberately.** The header's `my_absorption` values were hand-estimated for ~60 keV (a representative hard-X-ray/synchrotron energy) precisely because a steel 18650 can needs that much to be imaged in transmission at all. If you run at a very different energy, or care about quantitative attenuation, recompute `my_absorption` with the `xraylib.CS_Photo(Z, E_keV)` recipe the header gives — X-ray photoelectric attenuation scales roughly as `E⁻³`, so the fixed placeholder values are only valid near the one energy they were computed for.
4. **The neutron/X-ray contrast flip.** Run the *same* cell through both your McStas and McXtrace instruments and compare which shell dominates attenuation in each. You should see the header's claim directly: lithium-dominated for neutrons, cobalt-dominated for X-rays — the steel can should also read as noticeably more absorbing to X-rays than it did to neutrons.
5. **CT**, as in the McStas track: rotate the sample, collect a stack of radiographs at different angles, and reconstruct.

## Other interesting things to try

- **Solid centre pin instead of a hollow mandrel.** Both instrument headers suggest swapping the mandrel's `Vacuum` material for a polyethylene-based one (some real cells have a solid plastic winding pin) — a one-line change with a visible effect on the core of the image.
- **Quantify the placeholders.** Replace the hand-estimated `my_absorption` values with proper ones — `ncrystal_mcstasunion` (or `nctool`) for the neutron side, the `xraylib.CS_Photo` recipe for the X-ray side — and see how much the simulated images actually shift relative to the current order-of-magnitude estimates.
- **Uneven / local ageing.** The current geometry is perfectly cylindrically symmetric, so it can't show localised lithium plating or uneven wetting — exactly the kind of defect real neutron imaging studies (like the cited Ziesche paper) are used to catch. Splitting one shell into angular sectors with different `cfg`/density settings, rather than one uniform ring, is a genuine step up in Union geometry complexity and a good stretch goal.
- **Pair a neutron/X-ray image as one labelled training example.** Given the school's overall synthetic-data-for-AI framing, treat a matched (neutron radiograph, X-ray radiograph, ground-truth geometry) triple from this same cell as a toy supervised-learning sample — a small, concrete bridge back to the AI sessions later in the week.
- **Beyond cylindrical cells.** Both headers flag that pouch/prismatic stacked-electrode cells would need `Union_box` stacks instead of concentric `Union_cylinder` shells, and aren't covered here — a natural extension for anyone who finishes early.
